# Shared assistant providers
Approved in chat: assistants use the configured text providers offered by Threads, one at a time, retaining identity, history, memory, projects, voice, permissions and explicit task approvals. Existing provider adapters/sign-ins and model discovery are reused. Unsupported or unavailable providers remain visible with a reason; they do not silently disappear or fall back to another account/model.

Assistant conversation must be independent of the scheduled ApexAgent monitor. Ordinary replies cannot execute local tools, MCP, plugins, subagents or mutate project files. Explicit assistant operations remain in the existing host approval/task path. Provider isolation is enforced by the adapter/protocol and process boundary, never just model instructions. Monitor behavior is unchanged. All known text providers (Claude, Codex, Gemini, Grok, Muse, APIs) are discoverable. A provider without a verified isolated adapter on this machine is visible but refuses a reply with an actionable reason; notably Antigravity's shared background service must not inherit assistant authority.

Switching uses exact assistant revision and does not create a visible thread. Preserve reported usage and unknown values honestly. Existing model/reasoning/speed support applies; no model or credential invented. No new dependencies. Verify mocked adapter contracts plus real configured providers and native switching, stop, relaunch and task approvals. Build only from release after native acceptance; stale DMGs already removed. No merge/push authorized.

Implementation rulings: CLIs without a model catalog offer an explicit provider default (persisted as null) and may retain a configured model/reasoning choice; no fabricated account catalog or new arbitrary IDs. Native Gemini discovery is independent of Threads' Antigravity precedence. Private OAuth copies never receive refresh authority: Codex whitelists sufficiently fresh access/id/account data with an empty refresh token; canonical apps retain refresh ownership. Near-expiry connections fail with a renewal explanation. Grok session maps preserve selection and expiry metadata while stripping every refresh secret; an inactive old entry cannot veto a fresh selected entry. These behaviors preserve existing sign-ins instead of adding a competing refresher.
