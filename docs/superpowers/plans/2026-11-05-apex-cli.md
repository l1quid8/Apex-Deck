# Apex Deck CLI Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans task by task. Cast implements; Null owns design, reviews evidence, and releases the next task. Do not create another plan or dispatch additional implementers.

**Goal:** Build a real terminal client for Deck's shared multi-agent threads, following the approved CLI mockup and the app's routing and permissions.

**Architecture:** A Rust `apex` binary connects to the existing daemon's local IPC endpoint using protocol 1. The daemon remains authoritative for messages, routing, configuration, approvals, runners, and persistence. One language-neutral command catalog supplies app and CLI metadata; typed client handlers execute existing daemon commands.

**Tech stack:** Rust workspace, Tokio, serde, Ratatui with its Crossterm backend, existing apex-daemon IPC/protocol and apex-provenance receipt verification. Pin dependencies in Cargo.lock during implementation after checking the repository toolchain.

**Spec:** `mockups/apex-cli-v2.html` is the approved visual/interaction reference, not working product code. The requirements below record the subsequent chat decisions and take precedence over sample/mock behavior. ## Accepted product behavior

- Welcome shows up to three actual recent threads, newest first, plus exactly `/ for commands · @ to pick an agent · Esc to stop`. With no threads, show an honest empty state. No fake readiness checks or repeated folder/team line. `/help` opens the command menu.
- The terminal keeps the mockup's header/navigation, transcript, full-width multiline composer, and bottom status. Welcome and thread rows support arrows/Enter and mouse selection when mouse input is enabled. `/threads` opens its picker with one Enter; `/threads <name>` opens a unique case-insensitive prefix match. Multiple matches keep the filtered picker open; no match reports `No thread named <name> · /threads to list`.
- `@` completion lists the current members, then `@all` last. Tab/Enter inserts the same completion at the cursor. Unknown names never turn into broadcast. Ordinary message text, including mentions, goes to `room_post`; the daemon resolves targets.
- In Mention policy, initial/reset untagged routing uses the first eligible agent; explicit mentions select subsequent untagged responders, including multiple agents and `@all`. Respect existing named-only exclusions and other policies. Stars mean the daemon's effective eligible untagged target set, not an invented lead. RoundRobin scheduling remains daemon-owned; a star does not promise reply order.
- Opening a saved thread retains that thread's responders. `/new` creates a genuinely empty thread with zero agents, no sample replies, and Mention policy. `/add` is the recovery path. `/clear` deletes shared thread messages everywhere while retaining members/settings and resetting routing according to the existing daemon behavior.
- `/clear` first asks: `Delete this thread's messages everywhere? Agents and settings stay.` Default is Cancel. `/compact`, `/curate`, and `/curate undo` are thread-wide existing operations; reject agent arguments. Preserve the daemon's summarizer choice and history/curation behavior.
- `/stop` stops all current-thread agents; `/stop @name` stops one. Idle Esc is a no-op. Active Esc requests stop and reports `Stopped.` once on confirmation. Closing a picker with Esc must not accidentally execute a selected command; active work is still stopped.
- `/model @name` opens the daemon-backed model picker for that participant; without a name, pick a member first. `/access` opens the existing access levels and their real effects, requires an explicit selection, and applies through the protected command path. No invented permission levels.
- `/agents` shows membership, models, activity, and stars. `/usage` shows the available per-agent usage from state, with unknown values labeled unavailable. `/plan` toggles thread Plan through the daemon. Goal/loop syntax and limits match `src/runner/commands.ts`, `client.ts`, and `types.ts`, including pause/resume/clear; starting requires a review of workers and finite limits before submission.
- Messages and tool output are rendered as inert text. Strip terminal control sequences (including OSC/CSI and embedded escape bytes); retain ordinary newlines and tabs. Do not execute generated UI payloads or send interactive-answer support the CLI does not implement.

## Code anchors and necessary correction

- `crates/apex-daemon/src/ipc.rs`: endpoint resolution and async local stream; `paths.rs`: data-dir resolution. The endpoint is the data directory's `daemon.sock` on macOS. Use these APIs rather than reconstructing a path.
- `protocol.rs`: newline-delimited JSON `{id,cmd,args}`, out-of-order replies, `{seq,event,payload}` events; hello returns `host_id`, `boot_id`, `last_seq`, `resumed`, capabilities, and frame limit. Resume uses `{since:{boot_id,seq}}`.
- `local_call.rs::Client::reply` intentionally drops unrelated frames. Do not use that client for a streaming TUI. Add a separate multiplexing client without changing existing CLI callers.
- `crates/apex-core/src/room.rs::resolve_targets` owns policy, sticky targets and named-only filtering. `RoomSnapshot.last_targets` alone is insufficient for stars.
- `crates/apex-host/src/host.rs::room_state` is synchronous and reads a checkpoint while turns can hold the async room lock. Do not introduce blocking async-lock acquisition into this function.
- `src/composerMenu.ts::COMMANDS` is menu metadata; `src/commands.ts::parseComposer` is a separate parser. The registry work must connect these rather than copy their arrays.
- **The earlier "one daemon addition" estimate omitted protected authority.** Local IPC proves local transport, not authority for every command. `Command::requires_provenance`, `desktop/provenance.mjs`, and `crates/apex-provenance/src/main.rs` protect configuration, approval decisions, Plan and runner mutations. The broker currently pins the app and daemon, not a terminal binary. Production admission is a separate required task below, not a flag to turn off checks. An unsigned development CLI must show the refusal. Fixture success cannot be called production acceptance.

## File boundaries and interfaces

- Create `crates/apex-cli/` with `src/{main,args,client,state,input,ui,commands,authority}.rs`, `src/lib.rs`, and `tests/{transport,commands,terminal}.rs`. Binary name `apex`; add the crate to workspace members/default-members. Keep existing `apex-daemon` management commands intact.
- Create `shared/composer-commands.json` and `src/composerCommandRegistry.ts`. Catalog entries: `key`, `label`, `detail`, `surfaces` (app/cli), `handler` (stable ID), `argumentMode` (none/required/picker), `scope` (client/thread/participant). Include the app's existing deferred/image entries as app-only, preserving its behavior.
- CLI `client.rs`: `connect(data: &Path, since: Option<Cursor>) -> Result<Client, ClientError>`; `Cursor { boot_id: String, seq: u64 }`; `Client::request(cmd: &str, args: Value) -> Result<Value, ClientError>`; separate bounded event receiver. One reader task dispatches replies by numeric ID and events by sequence. Connection errors resolve every pending request.
- CLI `state.rs`: `AppState` owns connection status, selected room ID, selection generation, room states, draft, menus, and unresolved submissions. `apply_event(&mut self, envelope: Value)` never attributes an event to a room by the current selection alone.
- CLI `commands.rs`: deserialize catalog handler IDs into `HandlerId`; `parse_input(text: &str) -> ParsedInput` uses longest catalog command match (including `curate undo`); `dispatch(handler: HandlerId, args: &str, context: &mut CommandContext) -> Result<(), CommandError>`. Menu/help and dispatch availability use this same typed handler table. Unknown handler IDs fail catalog validation.
- CLI `authority.rs`: `authorize(command: Value, data: &Path) -> Result<Value, AuthorityError>` returns the original permitted ordinary command or an existing-format `provenance_execute` envelope. It verifies receipt signature, domain/kind, UID, canonical data directory and exact command; it cannot create or configure a trusted identity.

## Review focus

1. Lost acknowledgements must not duplicate a message or repeat a destructive command (Task 2).
2. Old-room events and snapshot races must not corrupt the newly selected thread (Tasks 1, 2, 4).

4. Pasted multiline text, Unicode width and terminal escape sequences must not send unexpectedly or corrupt the terminal (Task 4).
5. A fixture or signed binary must not create an unaudited authorization shortcut; denial and expired approvals remain visible (Tasks 3, 6).
