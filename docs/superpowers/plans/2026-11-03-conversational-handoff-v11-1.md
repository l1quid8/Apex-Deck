## Product contract

1. **Handoff:** Alfred saves a natural sentence identifying the destination/team. The attached progress pill reflects observed execution, and hover/focus reveals a quiet grey Stop without shifting layout. Keyboard users can reach Stop; on a device without hover, expose it through focus/tap or the open progress popover. Use an accessible name such as `Stop Muck and Null`.
2. **Clarification:** Preserve the original request while asking only the next missing item: project, existing/new thread, or agents. Existing/new thread options remain available. Agents support 1–10 ordered, distinct saved workers; the first selected leads. Preserve typed order, show the lead and team preview before Start. Enter toggles the highlighted worker; Start or Cmd/Ctrl+Enter launches. Ordinary Enter with no highlighted worker must not launch.
3. **Paused work:** Show `Waiting for you` and the actual worker question. For a continue/stop question, only an explicit Continue/Stop button or the host's exact plain-answer allowlist resolves it directly. Any other model-proposed resume/stop requires a matching confirmation button before changing execution. `No, wait for me`, `What did step 12 do?`, `hmm`, closing the form, and unrelated messages leave the worker waiting. Other question types keep their actual question schema; do not treat every question as yes/no. A plain yes never substitutes for an approval or resolves multiple questions.
4. **Stop:** A Stop click or a host-recognized standalone human stop targets the selected active task; other model-interpreted stops require confirmation. `Also check stderr and don't stop on warnings` must not stop it. `Don't give it to Muck` excludes that target or asks who instead; it does not cancel a job already with Hyke. Escape closes overlays first, may cancel thinking/pre-start work when no overlay is open, and never stops a running worker just because the user is editing text.
5. **Handover:** The popover's `Hand the rest to …` action uses the latest confirmed state after stopping the old attempt, not the inspected historical position. Keep work already performed, execution-folder context, pending-note ownership, and the original request. Never promise to undo a step or infer file contents from a step count.
6. **Composer:** A fixed-height, quiet `Add to this task · Run afterward` line selects a mode. Enter/Send commits once. Adding a note does not interrupt; it waits in a durable `Queued for …` row. Cmd/Ctrl+Enter or explicit Steer uses Deck's existing warning and preferences; cancelling that warning leaves the note queued.
7. **Queue timing:** Distinguish a worker **turn**, a task **attempt**, and accepted task completion. A note for a task-owned execution room waits until the whole active attempt settles, never between tool commands or while another selected worker is still running; it then uses a deliberate same-task continuation. Say `Hyke reads this when he finishes`; explicit Steer is the only route to reach him sooner, with the existing interruption warning. `Run afterward` creates a separately admitted successor task in the authorized project folder, held until the predecessor is `done`, so an unaccepted isolated result is never silently applied or assumed present in a new checkout. At `ready_for_review`, say `Waiting for this result to be accepted`. If the predecessor stops/fails/needs the user, hold the follow-up visibly. Jigga accepted this timing decision; the prototype alone does not settle the distinction. Use existing task/continuation machinery and stable delivery receipts, not a second scheduler.
8. **Progress:** Counts come from the current worker's reported to-do list; they are reported checklist progress, not proof that commands succeeded. Without a list, show `working` plus recent observed activity. Keep a multi-agent team visible and show who leads; do not sum incompatible per-worker lists. The popover shows view-only history and real output. Round 1 temporarily offers only `Try again` after a settled Stop; Round 2 replaces that recovery action with handover when supported. Neither acts on the inspected historical position.
9. **Lifecycle:** Support waiting to start, needs-OK, running, stopping, stopped, needs-you, couldn't-start, disconnected/unknown, ready-for-review, and done. Alfred summarizes real worker outcomes and selected milestones in plain language. Suppress redundant new ledger bubbles while retaining all underlying task records and existing execution details.

## Proposed contracts and file boundaries

Names in this section are proposed, not claims about existing APIs. Add optional/defaulted serialized fields and a new advertised capability, `assistant_conversation_handoff_v1`; older clients/hosts retain their existing task UI. Host ids, worker ids, revisions, request ids, and attempt ids remain authority-bearing; display names never replace them.

- `personal.rs`: add `PendingHandoff { id: String, revision: u64, source_event_id: String, original_request: String, brief: String, project: Option<ProjectRef>, destination: Option<TaskDestination>, missing: HandoffSlot, selection_event_ids: Vec<String> }`, where `HandoffSlot = Project | Thread | Workers`. Add a defaulted `saved_reply: Option<PreparedPersonalReply>` on the source `PersonalEvent`, not on the visible `PersonalMessage`. The private prepared record holds the normalized finished reply, cost/provenance, staged personal effects, and frozen ordered delegation manifest with stable `event:index` request ids and announcement/message ids. Persist it in the personal store before any child admission. It is the sole recovery payload; do not duplicate it in project task records. Existing personal API responses serialize events, so add a centralized outbound personal view that omits `saved_reply` from list/get/mutation responses; retain full internal reads for recovery and keep notification events identity/revision-only. Add saved last-used destinations scoped by exact `ProjectRef`, and permanent announcement receipts keyed by announcement id containing task id and message id. New-conversation clears unresolved routing drafts without deleting task history.
- `assistant_tasks.rs`: add `announcement_gate: Option<AnnouncementGate>` containing only immutable announcement id, assistant/source-event/message references and optional release time. The gate carries no saved reply text, memory mutations, cost/provenance envelope, helper assignments or other private personal commit payload; the ordinary authorized task brief remains part of task admission. Every held child points to an already-durable personal source record. Recovery reads that record and reuses the same ordered descriptors, rather than regenerating them or recovering private data from a task. Add typed durable `followups`, `conversation_events`, and current attempt-bound `progress`. Add optional `new_thread_title` to `TaskDestination`; it is display data, not an identifier. Preserve ordered distinct `workers`, with the first worker acting as lead in initial dispatch and handover.
- New `personal_handoff.rs`: focused host orchestration for draft selections, gate reconciliation, controls and follow-up admission. Keep storage transitions in the existing stores and execution in `assistant_service.rs`; register the module in `lib.rs`. Add `classify_plain_handoff_reply(text: &str) -> PlainHandoffReply`, returning `Stop | Continue | Other`, as the bounded deterministic control boundary described below.
- New `assistantHandoffModel.ts` and `AssistantHandoff.tsx`: pure view-model derivation and small pill/popover/clarification/composer-line components. Integrate into `ApexAgentAll.tsx`; avoid a broad ChatPane rewrite.

| --- | --- | --- |

| `personal_handoff_followup` | `requestId`, `taskId`, `expectedTaskRevision`, `mode` (`note` or `after`), `text`, ordered target worker ids | Durable follow-up id and queue state, bound to the current run or task boundary. |
| `personal_handoff_followup_action` | `requestId`, `taskId`, `followupId`, `expectedTaskRevision`, `action` (`edit`, `remove`, `steer`), optional replacement text and existing steer-consent scope | Updated durable follow-up/control receipt. Renderer cannot claim receipt/delivery before the host does. |

`TaskConversationProgress` contains `task_id`, `run_id`, participant id, observed time, reported todo items (optional), latest observed activity (optional), and links to actual work-step/message ids. `TaskConversationEvent` contains a stable event id, task/run/worker identity, source room event identity, kind and bounded evidence payload. `TaskFollowup` contains stable id/request id, source human event id, mode, target workers/run, body, state (`queued`, `delivering`, `delivered`, `held`, `removed`, `uncertain`), task-owned continuation receipt identity, and optional successor task id. A delivery with a lost acknowledgment is reconciled through its stable task request id; it is not blindly resent.

Task snapshots advertise `available_handoff_actions` for the current host/task state. Round 1 does not advertise handover or follow-up modes; clients must not infer support from the base capability alone. Task 4b advertises handover only after its command is implemented; Task 5 advertises note/after/Steer support only after durable delivery is available.

**Deterministic control boundary:** Match the entire authenticated human message after trimming, case folding, collapsing whitespace, and removing a trailing run of `.` or `!`; preserve question marks, quotes, negation and all other words. The fixed Stop set is `stop`, `stop here`, `cancel`, `cancel that`, `no, stop here`. The fixed Continue set is `yes`, `yes please`, `keep going`, `carry on`, `continue`, `go ahead`. These are whole-message matches, never substring/token matches; `yes?` and `stop?` remain questions. Continue is eligible only for one selected live continue/stop question; it never approves access or starts a new job. Stop still requires an unambiguous selected task. All other messages can be understood conversationally by the reasoner, but a proposed stop/resume produces `Stop Hyke?` / `Keep Hyke going?` with explicit buttons and leaves execution unchanged. Bind confirmations to assistant/task/run/question id and revision, revalidate on click, and reject stale or duplicated confirmations. Quoted/external/model text cannot enter this allowlist path. This narrow host rule replaces unsafe execution guesses; it does not replace natural-language routing with the mockup parser.

## Review focus

1. Crash/cancel between private reply save, task preparation, personal announcement commit, gate release and dispatch: no model replay, private reply in a project task record, invisible launch, duplicate task, or lost cancellation. Owned by Task 1.
2. A short selection or stale UI chooses a different project/team after grants change: keep the original scope, revalidate, and never silently select a default. Owned by Tasks 2–3.
3. A stop/redirect races task completion, a long command, another worker, or cleanup: remain stopping until the targeted old run settles; preserve edits and avoid overlapping writers. Owned by Tasks 4a–4b.
4. An ambiguous reply, model misclassification, closing a worker question, or a queued note accidentally resumes/approves work: leave execution unchanged until an allowlisted direct reply or bound explicit confirmation. Owned by Tasks 2, 4a and 5.
5. Stale progress, a missing/changed checklist, multi-agent events, or historical inspection produces false counts or artifact claims: project current evidence only and never mutate from inspection. Owned by Tasks 6–7.
